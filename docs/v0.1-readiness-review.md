# v0.1.0-alpha.0 — readiness review

> **⚠️ Stale (2026-05-25).** This review covers the `v0.1.0-alpha.0` core
> only — it predates cloud escalation (A.10–A.12), question-intent triage
> (A.13), on-demand training (A.14), and the 2026-05-30 learning-loop
> remediation. For current state see
> [`docs/2026-05-30-remediation-plan.md`](2026-05-30-remediation-plan.md).
> Kept as a point-in-time record of the original ship decision.

This document captures the honest, multi-angle consensus assessment used
to gate the first public alpha release of Lamark. It is preserved here
rather than rewritten into marketing copy on purpose: future contributors
should be able to see what shipped, what was deferred, and **why** — at
the moment of the decision.

The review was conducted on 2026-05-25 against the snapshot tagged
`v0.1.0-alpha.0`.

---

## A. Five-angle assessment

### 1. Installability & first-run UX

**Strong:**
- `install.sh` with `curl|bash` entry point follows the Ollama/Hermes
  muscle memory. Preflight checks (OS/arch/GPU/docker/python3/git) are
  thorough, idempotent.
- Unified `lamark` CLI surface is well-scoped — covers the full
  lifecycle (setup → serve → chat → train → status) without exposing
  internals.
- Hardware tier dispatch (`hardware.py` → `model-registry.yaml`) is the
  correct abstraction. The user doesn't pick a model; hardware does.

**Weak:**
- **No third-party install has happened.** Both verifications were on
  Sparks the author controls. The "someone other than the author can
  install" success criterion is unmet by the author's own definition.
- Sudo dependency for systemd timer installation is a UX cliff in a
  `curl|bash` flow. Without sudo the nightly retrain silently degrades
  to manual.
- The cloud-first branch of `lamark setup` was never executed end-to-end
  — only logic-reviewed.

### 2. Identity & memory architecture (the product itself)

**Strong:**
- **L1 via `chat_template.jinja` is the single best design decision.**
  Identity is base-model-agnostic, LoRA-agnostic, and survives
  `switch-base`. Zero retraining cost.
- L2 cross-session recall verified on two independent Sparks with the
  Moscow/green-tea test. A real, falsifiable claim with evidence.
- `LAMARK-PATCH A.4` cleanly couples runtime memory → training data.
  The Lamarckian flywheel exists in practice.

**Weak:**
- L3 ROME is deferred — without it, fact bake-in is functionally just
  retrieval (same as RAG). The differentiation narrative leaks if a
  user pokes.
- L4 is 10× below Allen-Zhu's extractability threshold. The LoRA
  pipeline works but does not yet **do what LoRA is for** on a fact
  scale that matters. Calling cycle 4 "trained" is generous.
- Plaintext `~/.lamark/archive/` JSONL is a Reddit-post-away from being
  a v0.1 critical issue.

### 3. Operational robustness

**Strong:**
- Adapter location moved to `~/.lamark/adapters/` after `/tmp` wipe on
  Spark-01. The fix is architectural, not just procedural.
- `train-history.jsonl` + `min_pairs` threshold gating is the right
  pattern — cadence trigger + content gate prevents empty training
  thrash.
- LoRA adapter auto-discovery from `adapter_config.json` glob is robust
  to manual user intervention.

**Weak:**
- **Spark-01 is still hung** after `apt upgrade + vLLM load` combination.
  Reproducible failure mode that requires physical reset. Root cause
  unknown. Shipping with this unresolved means a stranger who reboots
  their Spark mid-install might brick theirs too.
- Cycle 1-3 adapters loss surfaced that persistence wasn't audited end
  to end. The fix is in, but suggests other "where does state live"
  questions deserve a pass.
- Nightly systemd timer never observed firing. We only ran
  `lamark train --now` manually. The whole hybrid-retrain UX — the
  thing differentiating Lamark from "run a script" — is unverified.

### 4. Model/runtime stack honesty

**Strong:**
- `vllm/vllm-openai:v0.21.0` upstream stable + `qwen3_xml` tool parser +
  LoRA + MoE expert parallel all working simultaneously is non-trivial
  integration work. It works.
- Multi-arch arm64+amd64 means Spark and consumer x86 paths share
  infrastructure. Good leverage.

**Weak:**
- **Consumer GPU path is fictional.** The registry has 14B/7B/1.5B
  entries that have never run on a 4090/3090/Mac. We claim hardware
  support we haven't validated. Spark-specific quirks (`flash_attn`
  purge, `eager_loader_patch`) may not apply or may be actively wrong
  on sm_89 Ada.
- vLLM 0.21.0 pinned but not justified in writing. When 0.22 drops and
  someone runs `pip install -U`, what breaks? `peft + trl` ad-hoc
  install inside the container is especially fragile.

### 5. Honesty of the "v0.1 alpha" framing

**Strong:**
- The "what's deferred" list is unusually candid. Most projects hide
  L3-not-built and Allen-Zhu-threshold-not-met. This one names them.
- Two-Spark verification of L1+L2 is genuine reproducibility, not
  "works on my machine."
- Scope is bounded and testable: "someone other than the author can
  install and use it."

**Weak:**
- That bar — third-party install — is not yet met.
- Earlier project docs implied L3 was Phase 1. Quietly relabeling
  deferred work as "Phase 2" should be done with explicit
  acknowledgement (this review counts).

## B. Mitigations applied before tag

The review surfaced three issues that were fixed in-place before the
tag (rather than deferred):

1. **Thinking-mode leakage in chat output.** Qwen3 thinking-mode was
   leaking `<think>...</think>` reasoning into the assistant message.
   Patched by forcing `enable_thinking = false` at the top of the
   Lamark-customized `chat_template.jinja` (in `build_template.py`).
   Verified clean direct output on simple and complex prompts.

2. **Consumer GPU path silent claims.** Added `tested: false` flag to
   non-Spark entries in `scripts/model-registry.yaml`; `lamark setup`
   now warns and requires explicit `y` confirmation when the user
   picks an untested tier; README hardware-tier table now has a
   "Status" column.

3. **Russian content in user-facing code.** All bilingual Q&A pairs
   removed from `seed_identity*.py` and `seed_session.py`. The README's
   Russian-language section was removed. Repo is English-only outside
   `vendor/hermes`.

## C. The single thing most likely to embarrass us

**A Reddit user with a 4090 runs `curl | bash`.** Hardware tier dispatch
picks `qwen-3.6-14b-dense` from the registry. The new "experimental
tier" warning fires — but if they say `y`, they hit one of:

- vLLM crashes loading the dense Qwen model on sm_89 Ada because the
  `flash_attn` purge in our container entry was tuned for the Blackwell
  ABI mismatch and is actively wrong on Ada (where `flash_attn` should
  remain installed).
- vLLM starts but produces garbage tokens because `eager_loader_patch`
  is a Spark unified-memory workaround that does nothing useful on
  discrete VRAM and may interfere with the standard load path.
- Everything serves correctly but `lamark chat` UX has some other
  surprise we haven't seen yet.

The mitigation in place is the explicit warning + `y` gate. The proper
fix is to make the Spark-specific quirks conditional on `is_spark` and
test on a real 4090. That's Phase 2.

**Secondary embarrassment risk** was thinking-mode reasoning leakage in
every chat. Fixed pre-tag (see Mitigation 1). The screenshot that would
have defined the project's public perception isn't possible to take any
more.

---

## D. Verdict

**Ship with sharp asterisks.**

Phase 1 alpha is a defensible release because:

- The core architectural decision (L1 via chat_template) is genuinely
  innovative and verifiably works on two independent hosts.
- The mitigations applied pre-tag close the highest-probability
  embarrassment vector (thinking-mode UX) and explicitly gate the
  highest-impact one (consumer GPU + Spark quirks).
- The deferred list is documented honestly in CHANGELOG and this file,
  not hidden.

It is not "ship cleanly" — the third-party install criterion isn't met
and Spark-01 remains hung. But waiting for those to clear before public
visibility means waiting on someone else's calendar (testers) and
on physical reset access. The right move is: ship, expect bug reports,
treat the first 5 issue reports from non-author users as the
phase-1-validation-experiment that the author can't conduct alone.

---

## E. Phase 2 priority order

1. **Resumable HF download.** First failure mode after install — a
   network blip costs a 67 GB restart. High frequency, low effort.
2. **Consumer GPU validation on a real 4090.** Replaces guessing with
   evidence. Removes the asterisk that this document calls out.
3. **L3 ROME prototype.** ~50 LOC patch to EasyEdit (`nethook.py` +
   `compute_v.py` + `repr_tools.py`) for transformers 5.x dict-output
   compat. Validates the unconditional-recall claim.
4. **Encryption at rest.** age-encrypted archive + adapters with
   passphrase. Closes the privacy headline risk.
5. **Spark-01 root cause.** Why does `apt upgrade + vLLM load` brick
   the host? Until this is understood, every Spark user is one upgrade
   away from a manual reset.

L4 LoRA at 1000+ pairs is deferred to Phase 3 — that's a research-pace
deliverable, not engineering.
